# SQL Operations Toolkit

![PostgreSQL](https://img.shields.io/badge/PostgreSQL-13%2B-336791?logo=postgresql&logoColor=white)
![tests](https://github.com/eftekhar-azahar/sql-operations-toolkit/actions/workflows/tests.yml/badge.svg)

A PostgreSQL reporting toolkit for IT operations: SLA compliance, MTTR/MTBF, backlog ageing, breach risk, escalation load and problem-ticket candidates, built on an ITSM ticket schema covering incidents, service requests, change requests and problems.

It answers the questions an operations or service-delivery team gets asked every week:

| Question | Where |
|---|---|
| Did we meet SLA this month, per ticket type and priority? | `v_monthly_sla_compliance`, `fn_sla_compliance()` |
| Which open tickets are about to breach? | `fn_breach_risk()` |
| How old is each team's backlog? | `v_backlog_aging` |
| Which services fail most often, and how fast do we recover? | `v_service_reliability` (MTTR, MTBF) |
| Where do escalations pile up? | `v_escalation_summary` |
| Which repeat incidents should become a problem record? | `fn_problem_candidates()` |
| How do we freeze a signed-off month so it never changes? | `fn_close_month()` + `sla_monthly_snapshot` |

> All data is synthetic, generated by `sql/02_seed.sql` with a fixed seed (about 2,400 tickets, May–October 2026). Services, teams and SLA targets are illustrative.

## Quick start

```bash
git clone https://github.com/eftekhar-azahar/sql-operations-toolkit.git
cd sql-operations-toolkit
./run_all.sh            # creates database itops_demo, loads everything, runs tests and the report
```

Uses the normal `PGHOST`, `PGPORT` and `PGUSER` variables. Or run the files yourself in order:

```bash
psql -d itops_demo -f sql/01_schema.sql
psql -d itops_demo -f sql/02_seed.sql
psql -d itops_demo -f sql/03_views.sql
psql -d itops_demo -f sql/04_functions.sql
psql -d itops_demo -f tests/test_toolkit.sql
psql -d itops_demo -f sql/05_analytics.sql
```

## Schema

```
support_group ─┐                 ┌─ sla_target (type, priority → response/resolve minutes)
service ───────┼──► ticket ◄─────┘
               │      │
               └──────┴──► ticket_event   (assigned, escalated, pending_customer,
                                           resumed, resolved, reopened)
sla_monthly_snapshot  ◄── fn_close_month()
```

- **SLA clock:** 24×7, with customer-pending time (`pending_customer` → `resumed`) excluded. For business-hours SLAs with weekends and holidays, see [sla-calculation-engine](https://github.com/eftekhar-azahar/sla-calculation-engine).
- **`ticket.resolved_at`** is always the final resolution. Reopens are kept in the event log.

## Files

| File | Contents |
|---|---|
| `sql/01_schema.sql` | Tables, constraints, indexes (partial index for open tickets) |
| `sql/02_seed.sql` | Reproducible synthetic data: tickets, escalations, pauses, reopens |
| `sql/03_views.sql` | 5 views: `v_ticket_sla`, `v_monthly_sla_compliance`, `v_backlog_aging`, `v_service_reliability`, `v_escalation_summary` |
| `sql/04_functions.sql` | 4 functions: `fn_sla_compliance`, `fn_breach_risk`, `fn_close_month`, `fn_problem_candidates` |
| `sql/05_analytics.sql` | 10 analysis queries using window functions (`LAG`, `RANK`), `FILTER`, `percentile_cont` |
| `tests/test_toolkit.sql` | 7 checks: timestamp sanity, balanced pauses, view vs raw recount, function vs view, idempotent month close, input validation, owner-group consistency |

**Incident resolution time by priority (hours)**

| priority | resolved | p50 | p90 | worst | target |
|---|---|---|---|---|---|
| P1 | 33 | 2.0 | 4.0 | 40.2 | 4.0 |
| P2 | 161 | 2.9 | 7.9 | 70.9 | 8.0 |
| P3 | 613 | 10.9 | 25.2 | 85.1 | 24.0 |
| P4 | 420 | 31.6 | 71.9 | 118.1 | 72.0 |

The p90 sits right at target for every priority. The "worst" column is driven by reopened tickets: reopened incidents average 55.7 hours to final resolution against 18.5 hours for first-time fixes.
